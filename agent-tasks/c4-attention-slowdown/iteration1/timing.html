01

시간은 어디에 쓰이나? MEASURED

같은 축으로 비교한 전체 attention 시간. 모든 head의 비용을 합친 값입니다.

이 막대는 timestamp trace가 아닙니다. Flash의 반복 실행 구간을 종류별로 모아 이어 붙인 시간 비중입니다. 실제 순서는 아래 02에서 확인하세요. Pure GEMM과 내부 DMA는 별도 timer가 없어 GEMM 대기 + 내부 DMA로 함께 표시합니다.
Flash 구간시간 / ms전체 비중

현재 남은 차이

MCYCLE / 100,000 = ms. 각 구간은 3회 median입니다. 개별 median의 합은 전체 median과 약간 다를 수 있습니다. “기타·집계 차이”는 전체에서 나머지 표시 구간을 뺀 값이며 별도 계측 단계가 아닙니다. Host launch 시간은 제외했습니다.

02

무엇이 앞 작업을 기다리나? ORDER ONLY · NOT TO SCALE

한 head/group의 한 KV tile 실행 예시. 가로 폭은 순서를 보여주기 위한 것이며 측정 시간을 나타내지 않습니다.

일반 커널: phase 단위 직렬 실행

QK (모든 head) → softmax (모든 row)
→ PV (모든 head) → context 출력

일반 softmax는 이미 정규화한 P를 만듭니다. 따라서 PV 결과가 바로 context입니다. QK / softmax / PV는 서로 겹치지 않으며, GEMM의 head별 job도 순서대로 완료를 기다립니다.

Flash: head/group → KV tile 순회

Flash는 비정규화 probability로 PV를 계산하고 FP32 accumulator에 누적합니다. 최종 row sum으로 나누는 정규화가 별도로 남습니다. 다음 tile과 head/group도 앞 작업 완료를 기다립니다.

색 블록 = 그 자원에서 수행하는 작업 · 빈 칸 = 해당 attention 단계의 유효 작업 없음 · 점선 회색 = 제어/polling 대기. Control 행은 별도 연산 엔진이 아니라 core의 제어 흐름을 표시합니다. 아래 버튼으로 단계 설명을 선택할 수 있습니다.

병렬성과 완료 조건

Polling ≠ 유효한 연산 overlap. GEMM/DMA 동작 중 core가 완료 상태를 읽는 것은 제어상 동시 실행입니다. 그동안 다음 tile의 softmax나 누적을 진행하는 것은 아닙니다. SIMD worker 종료·publication 이후 다음 GEMM을 제출합니다.
03

단계 안의 병렬성은 어디에 있나?

“thread가 여러 개다”와 “서로 다른 단계를 겹쳐 실행한다”는 별개의 성질입니다.

SIMD: 여러 row / 원소를 나눠 처리

일반 SIMD 단계: 4 warps × 16 threads의 논리 작업 분배. Softmax는 warp별 query row, warp 안에서는 열을 분담합니다. 누적·정규화는 원소를 thread에 분배합니다.

4 warps × 16 threads가 매 cycle 64개 원소를 처리한다는 뜻은 아닙니다. Warp 스케줄링, FU/LSU 폭과 메모리 경합의 영향을 받습니다. Padding은 warp 0 하나의 16 threads만 사용합니다.

GEMM: MXU 내부의 공간 병렬 연산

설정은 16 × 16 MXU입니다. QK/PV job 안에서 여러 원소의 곱·누적을 처리합니다.

작은 query 수·padding에 따른 실제 PE 점유율은 이번 측정에 포함되지 않았습니다.

GEMM job 내부의 HBM load / 연산 overlap은 이 그림에서 분해하지 않습니다. 이번 timer는 job 완료 대기를 합쳐 측정합니다. 그림의 GEMM 블록은 전체 job 구간을 뜻합니다.
확인된 직렬화
head/group 간 · KV tile 간 · QK → softmax → PV → 누적 · GEMM과 SRAM DMA · DMA subword 전송 및 완료 대기
확인된 작업 분배
SIMD의 warp/thread별 row·원소 분담 · GEMM MXU 배열 내부 연산. Memory bank들이 존재한다고 이 copy 엔진이 모든 bank를 동시에 전송하는 것은 아닙니다.
04

HBM을 피했는데, 복사는 왜 남나?

SIMD는 LMEM xbar로 접근합니다. TMEM에 SIMD용 xbar가 없으므로 GEMM과 SIMD 사이에서 명시적인 SRAM copy가 필요합니다.

HBM 주소 공간

화살표 중 앞의 세 개는 tile마다 발생하는 SRAM copy입니다. 마지막은 최종 output store입니다. Q/K/V 입력은 job에서 HBM 경로로 읽으며, 최종 context는 HBM 주소 공간에 저장합니다. 중간 score/probability를 SRAM에 유지한다는 의미이지 HBM 접근 전체를 없앴다는 의미는 아닙니다.

32B TMEM beat ↔ 8B LMEM subword × 4. 한 command / 한 transaction 엔진입니다. 응답 또는 write commit을 받은 뒤 다음 subword로 넘어갑니다. 네 subword가 동시에 전송되는 구조가 아니며, 모든 32B chunk를 처리해야 다음 계산 단계가 시작됩니다. 위 칸 너비는 cycle 수를 뜻하지 않습니다.
