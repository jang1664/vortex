# Fixed-count polling diagnostic (2026-09-08 22:47 KST)

Existing `fpint_gemm_ffn_hw --pol 1` and `--pol 256` use the exact same
host/kernel binaries as GEMM comparisons. The kernel takes QDIR sentinel
0xDEAD and runs a fixed-count read/ALU loop without allocating/submitting GEMM.
The host checks kernel STATUS_OK and normal completion, but deliberately skips
output verification. Its printed PASSED must not be called GEMM correctness.

Each VCS entry repeats identically twice. Hardware job 4909 ran one excluded
warm-up plus five fresh-process samples per count. Ranges are [5662,5702] and
[23740,23878]; all post-run clock/UUID checks match the candidate. Instruction
counts are identical across modes: 5986 at one poll, 8536 at 256. Binary hashes
pass before/after both simulator and hardware launches. All jobs terminated;
the temporary launch links again select document mode.

The document shortfall is 1549 cycles at one poll and 1514 cycles at 256.
Thus a substantial gap exists without GEMM, while marginal polling costs are
close. The evidence rules out attributing the entire earlier gap to GEMM
arithmetic or DMA/HBM-switch contention generated by GEMM. It does not rule out
HBM effects on instruction fetch/ordinary loads, nor establish one removable
fixed overhead. Do not subtract this offset from acceptance cycle results.

Next inspect the hardware/simulation cycle-counter start/stop/reset boundaries
and startup instruction/data-cache traffic. This diagnostic supports narrowing
the cause before adjusting a DRAM residual parameter; no parameter changed.
